## Why this patch exists (the motivating failure)
This cycle an early 1.2 build shipped a prebuilt engine that **every GPU box silently declined** in favor of
a slow source build (the resolver matched engine rows by `tier == "gpu"` but the published manifest names
the tier `"cuda"`, and it only fetched the manifest when HEAD sat exactly on a tag). It reached users
because **CI never exercises the real download and run path**, and the release process let `VERSION` and
`versions.lock` drift. 1.2.2 closes that class of failure.

## Scope of 1.2.2 (one theme: a release cannot ship broken and pass green, and cutting one is safe)

1. **Manifest-resolution contract test (highest priority, low cost).**
   A test that fetches the ACTUALLY published `engines.json` (the per-release asset) for the current or
   latest release tag and asserts `scripts/bob/lifecycle.py` `_select_engine_row` selects a row AND the
   commit-match guard passes, for every published (component, os, arch, tier). This is the test that would
   have caught the `tier: "cuda"` vs `"gpu"` bug. Make it network-aware (skip cleanly offline, or run in a
   dedicated CI job) so it never breaks offline dev. Add a negative case (a deliberately wrong tier in a
   fixture must fail). Files: `scripts/bob/lifecycle.py` (`_load_engine_manifest`, `_select_engine_row`,
   `_latest_release_tag`, `prebuilt_available`), `tests/test_lifecycle.py` or a new `tests/test_release_manifest.py`.

2. **Real GPU inference in CI (needs the self-hosted runner).**
   The `acceptance-gpu` job in `.github/workflows/ci.yml` is scaffolded but gated off (`vars.GPU_RUNNER ==
   'true'`, `runs-on: [self-hosted, gpu]`), so CI has NEVER run a single token through a GPU; it only checks
   the binary loads (`--version`). Wire my Blackwell box as a self-hosted GPU runner, set `vars.GPU_RUNNER`,
   and make the job (a) resolve and DOWNLOAD the published prebuilt (not just `--from-source`), (b) run REAL
   inference through it on the GPU (extend `scripts/smoke.py`), and (c) assert the GPU tier marker. A broken
   engine or resolver must fail this job. Document the runner setup. (Windows GPU verification stays out of
   scope, no Windows GPU box, note it as a residual.)

3. **`bob release`: one command to cut a release safely.**
   A new verb that moves `VERSION`, the `versions.lock` `release` field, and `CHANGELOG.md` ([Unreleased] to
   the new version) together so they cannot drift, and optionally creates the tag. This prevents the exact
   drift that forced a 1.2.1 re-cut (bumping VERSION alone left `versions.lock` release stale, so `check_sync`
   flagged STALE and failed the gates). Files: `scripts/bob/registry.py` (one entry plus a handler),
   `scripts/bob/versions.py`. Do not run a full `bob lock` as part of it unless the model-sha false positive
   below is fixed first (see item 4). Acceptance: `bob release <x.y.z>` yields a consistent VERSION plus lock
   plus changelog in one step and `python -m bob.versions --check` passes.

4. **Kill the local `versions.lock` STALE false positive.**
   The committed lock has `sha256: null` for at least one model (Qwen3-Coder) while a dev machine's manifest
   has the real sha, so `python -m bob.versions --check` / `bob doctor` always reports STALE locally (it bit
   us twice this cycle and blocks a clean local gate). Fix it: either populate the real sha in the committed
   lock, or make `lock_text` / `check_sync` treat a null model sha as "unpinned, do not diff". Files:
   `scripts/bob/versions.py`, `versions.lock`. Acceptance: `--check` passes on a clean checkout locally.
